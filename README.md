# gigacrew

> [!WARNING]
> **Это личный проект, а не продукт для широкой аудитории.** Если вы попали в этот репозиторий
> сами, а не по прямому приглашению автора, — этот проект точно не для вас. Он не публикуется
> на PyPI, не поддерживается для сторонних пользователей, issue и pull request'ы не принимаются.

Консольная утилита для работы с кодом локального проекта: навигация по исходникам, поиск, правка файлов и запуск команд в терминале.
Перед запуском скопируйте `.env.example` в `~/.gigacode/.env` и укажите в нём адрес API, модель и реквизиты доступа — значений по умолчанию нет.
Для бэкенда GigaCode задайте `GIGACREW_PROVIDER=gigacode`, его адрес и `GIGACREW_USER_AGENT` (тоже без значения по умолчанию): токен берётся из `~/.gigacode/gigacode_token.json` — авторизуйтесь в официальном CLI GigaCode, — модели берутся из каталога бэкенда.

## Настройки

Настройки читаются из переменных окружения, файла пользователя `~/.gigacode/.env` (общий для всех
проектов), `.env` в корне проекта и `.env` текущей папки — в этом порядке приоритета. `.env` проекта —
часть репозитория, его может прислать кто угодно, поэтому настройки безопасности из него (и из `.env`
текущей папки) не берутся: адреса `GIGACREW_API_URL` и `GIGACREW_AUTH_URL`, `GIGACREW_VERIFY_SSL`,
`GIGACREW_CA_BUNDLE`, `GIGACODE_HOME`, `GIGACREW_CERT` и `GIGACREW_KEY`. Такие строки пропускаются,
gigacrew пишет об этом при запуске — перенесите их в переменные окружения или в `~/.gigacode/.env`.
Ключ доступа, модель, тайм-ауты, режим и остальные настройки работают и из `.env` проекта.

Сертификат сервера по умолчанию проверяется — и у API v2, и у бэкенда GigaCode: стандартными
корнями (certifi и системное хранилище). Если сервер подписан корпоративным УЦ, которого там нет,
укажите его корневой сертификат в `GIGACREW_CA_BUNDLE` (PEM). `GIGACREW_VERIFY_SSL=0` выключает
проверку явно — ключ и токен тогда можно перехватить подменой сервера, gigacrew предупреждает об
этом при каждом запуске.

## Установка

На PyPI пакета нет — ставится из клона репозитория:

```sh
uv tool install .
```

## Режимы и подтверждение команд

Режимов два, Shift+Tab или `/mode` переключает между ними:

- **авто** (`auto`, по умолчанию) — правки файлов без вопросов, изменяющие команды сначала
  смотрит модель-рецензент: она разрешает команду или передаёт решение вам;
- **план** (`plan`) — только исследование и план: правки и изменяющие команды заблокированы.

Прежние имена `manual` и `edits` (в `GIGACREW_MODE`, `--mode`, `/mode`) означают `auto`.

Команды, которые только читают проект (`ls`, `cat`, `grep`, `rg`, `git status/log/diff`,
`jj status/log/diff` — и в колоцированном с git репозитории, однострочники на Python, которые
лишь читают файлы), выполняются без вопроса в любом режиме.
Это решает локальный классификатор, без сети и моделей: команда разбирается деревом
tree-sitter-bash, Python-код — модулем `ast`. Он же объясняет, чем опасна остальная команда:
тесты и сборка исполняют код проекта, установка пакетов идёт в сеть, `rm -rf` и
`git push --force` — опасны. Всё незнакомое считается непроверенным.

`--untrusted-project` — для работы с недоверенным проектом, например ревью чужого PR
(gigareview): файлы проекта, его инструкции (`AGENTS.md`, `GIGACREW.md`) и скиллы становятся для
модели данными, а не указаниями, — и для основного агента, и для суб-агентов `explore`/`task`,
которые не видят промпт основного. Текст, обращённый к агенту, модель сообщает, а не выполняет.

Файлы с секретами (`.env`, ключи `*.pem`, `id_rsa`, `.npmrc`, `credentials.json`, всё в `.ssh/` и
т. п.) `read_file` и поиск не читают, даже с `-y`: модель может прочитать их только командой, а её
подтверждаете вы или рецензент. Правку `.env` — из него gigacrew берёт ключ доступа и настройки —
вы подтверждаете всегда, даже с `-y` (без вопроса — только с `--yes-all`); правку других файлов с
секретами — и в режиме «авто».

Временные файлы (черновые скрипты, сохранённый вывод команд) модель кладёт в `.gigacode/tmp/`
проекта: запись туда — обычная правка, в режиме «авто» она идёт без вопроса, а в git папка не
попадает. Запись в `/tmp` и другие места вне проекта вы подтверждаете всегда.

Изменяющую, но не опасную команду в режиме «авто» проверяет модель-рецензент — это один
запрос к модели. По умолчанию рецензент — модель чата (в том числе после `/model`), другую
задаёт `GIGACREW_REVIEWER_MODEL`. Рецензент видит ваши последние запросы, команду и выводы
классификатора, но не рассуждения агента и не вывод инструментов — содержимое файлов не может
его уговорить. Он разрешает только то, что явно нужно для вашей задачи и не выходит за
проект; в остальных случаях спрашивает вас и объясняет почему. Опасные команды, команды,
которые вы уже отклоняли, и команды при сбое рецензента всегда решаете вы. Если модели из
`GIGACREW_REVIEWER_MODEL` нет, при запуске выводится предупреждение и рецензент отключается:
тогда команды подтверждаются вручную. Ответа рецензента gigacrew ждёт не дольше
`GIGACREW_REVIEWER_TIMEOUT` (60 с) и без повторов: если модель тормозит, решение сразу
переходит к вам.

На вопрос можно ответить:

- `y` — выполнить один раз;
- `a` — выполнить и запомнить для проекта. Программа с подкомандой (`pytest`, `npm test`)
  запоминается вместе с безопасными аргументами, а также в обёртках вроде
  `pytest -q 2>&1 | tail` или `uv run pytest`. Остальное запоминается как точная команда.
  Разрешение действует в своём рабочем каталоге. Опасное не запоминается;
- текстом — отказаться и сказать, что сделать вместо этого (ответ получит модель).

`-y` снимает вопросы, кроме опасных операций (`rm -rf`, `git reset --hard`, правка `.env`, файлы
вне проекта…) и команд, которые классификатор не смог проверить: такую команду в режиме «авто»
по-прежнему смотрит рецензент, а затем, если он не разрешил, — вы; в режиме плана решаете вы.
`--yes-all` выполняет без вопроса всё, включая опасное и (в режиме «авто») непроверенные команды, —
используйте осознанно. В `-p` на вопросы отвечают только с клавиатуры: перенаправленный stdin
(`echo y | gigacrew -p …`) согласием не считается — без терминала ответ на вопрос «нет», а выбор
чата (`-r` без id) начинает новый чат.

Разрешения и журнал решений (что спросили, почему, что ответили, в каком каталоге и чем
кончилось) хранятся в `~/.gigacode/projects/`, а не в проекте. Поэтому репозиторий не может
принести с собой готовые разрешения. `/permissions` показывает разрешения,
`/permissions forget N` удаляет одно, `/permissions log` показывает последние решения.
В журнале видно и решения рецензента. Журнал не ведётся с `--no-save`; секреты в командах
(`TOKEN=…`, пароли в URL и флагах вроде `mysql -p…` и `curl -u user:pass`, заголовки с ключами,
токены сервисов) вырезаются, и `/permissions` показывает их вырезанными. Команда с секретом
правилом на диск не сохраняется: «всегда» для неё действует до конца сессии.

## Чаты

Диалог сохраняется после каждого хода в `~/.gigacode/projects/<ключ проекта>/chats/` — рядом с
разрешениями, а не в проекте: продолженный чат — это ваши запросы (по ним рецензент решает, что
нужно для задачи) и ваша модель, и файл из репозитория не должен выдавать себя за них. Рабочие
деревья одного git-репозитория делят чаты, как и разрешения. `-c` продолжает последний чат,
`-r ID` (или начало id) — выбранный, `-r` без id и `/resume` открывают список чатов. `--no-save`
(или `GIGACREW_SAVE_CHATS=0`) не сохраняет чат и журнал решений; историю ввода
(`.gigacode/history`, стрелка вверх) это не касается.

Чаты прежних версий из `.gigacode/chats/` проекта переносятся при первом запуске (оригинал
остаётся, только если перенести не удалось). Чаты, которые отслеживает git, — пришли с
репозиторием — не переносятся и не открываются; из проекта чаты больше не читаются. Вне
git-репозитория чаты не переносятся вовсе — не проверить, не пришли ли они вместе с проектом:
свои перенесите в `~/.gigacode/projects/<ключ проекта>/chats/` сами (путь gigacrew покажет при
запуске). Планы остаются в `.gigacode/plans/`.

## Скиллы

Скилл — готовая инструкция для типовой задачи: файл `SKILL.md` в своём каталоге.
gigacrew ищет скиллы в `.gigacode/skills/<имя>/SKILL.md` проекта и в `~/.gigacode/skills/<имя>/SKILL.md`
(общие для всех проектов; при совпадении имён побеждает проектный). Скилл, который симлинком
ведёт за пределы своего каталога скиллов (а скилл проекта — за пределы проекта), пропускается.

```markdown
---
name: release
description: Как выпустить новую версию пакета
---
Подними версию в pyproject.toml, обнови CHANGELOG и поставь тег. Версия: $ARGUMENTS
```

Вызов — `/release 1.2.0` (Tab дополняет имена скиллов, `/help` их перечисляет; аргументы
подставляются вместо `$ARGUMENTS` или дописываются в конец). Модель видит список скиллов с описаниями
и может загрузить подходящий сама. Каталог `.gigacode/skills/` коммитится вместе с проектом — планы,
история ввода и индекс в той же папке закрыты её собственным `.gitignore`.

## Хуки

Хук — команда оболочки, которую gigacrew запускает сам на событиях агента: отформатировать файл после правки,
запретить команду по своим правилам, прогнать тесты перед концом ответа, получить уведомление. Формат — как у
Claude Code, настройки — JSON (хуки из всех файлов объединяются):

* `~/.gigacode/settings.json` — общие для всех проектов;
* `.gigacode/settings.json` — проекта, коммитится;
* `.gigacode/settings.local.json` — личные, закрыты `.gitignore` папки (в проекте, где `.gigacode/.gitignore`
  создан раньше, добавьте строку `/settings.local.json` сами).

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "write_file|edit_file",
        "hooks": [{"type": "command", "command": "ruff format \"$GIGACREW_PROJECT_DIR\"", "timeout": 30}]
      }
    ],
    "Stop": [{"hooks": [{"type": "command", "command": "make test >&2 || exit 2"}]}]
  }
}
```

`matcher` — регулярное выражение на всё значение (пусто или `*` — любое), `timeout` — секунды (1…600, по
умолчанию 60). `"disableAllHooks": true` в `~/.gigacode/settings.json` выключает все хуки, а в файлах
проекта — только хуки проекта: хуки пользователя репозиторий выключить не может.

| Событие | Когда | matcher | Что может хук |
|---|---|---|---|
| `PreRequest` | перед каждым запросом к бэкенду GigaCode и перед повтором после 401 | вид запроса: `config`, `chat`, `probe` | обновить токен; код 2 — не отправлять запрос |
| `PreToolUse` | перед вызовом инструмента | имя инструмента | запретить вызов; решить, спрашивать ли подтверждение |
| `PostToolUse` | после вызова | имя инструмента | передать модели замечания (вывод линтера) |
| `UserPromptSubmit` | запрос отправлен | — | отклонить запрос; добавить к нему контекст |
| `Stop` | модель закончила ответ | — | вернуть её к работе с причиной |
| `SubagentStop` | суб-агент закончил | имя суб-агента | то же для суб-агента |
| `SessionStart` | старт, `/clear`, `/resume` | `startup`, `clear`, `resume` | добавить контекст в системный промпт |
| `SessionEnd` | выход, `/clear`, `/resume` | `prompt_input_exit`, `other`, `clear`, `resume` | — |
| `PreCompact` | перед сжатием истории | `manual`, `auto` | — |
| `Notification` | gigacrew ждёт подтверждения или ответа | `permission_prompt`, `question` | — |

Хук получает JSON в stdin: `session_id` (id чата), `transcript_path` (файл чата в формате gigacrew; пишется
после хода, при `--no-save` его нет), `cwd`, `hook_event_name`, `permission_mode` и поля события: `tool_name`,
`tool_input`, `tool_use_id`, `tool_response` (`{ok, content}`), `prompt`, `stop_hook_active`,
`last_assistant_message`, `agent_type`, `source`, `reason`, `trigger`, `custom_instructions`, `message`,
`notification_type`. `PreRequest` срабатывает только с провайдером `gigacode`, вне чата: в stdin — `cwd`,
`hook_event_name`, `request` (вид запроса), `reason` (`request` или `unauthorized` — повтор после 401), `url` и
`token_file` (файл токена официального CLI; после хука gigacrew перечитывает его, так что обновлённый токен
уходит в этом же запросе). Автоматические повторы того же запроса (сеть, 5xx, 429) хук не вызывают.
Имена инструментов и параметров — gigacrew, а не Claude Code: `read_file`, `write_file` и `edit_file`
принимают `path` (не `file_path`), `run_shell` — `command`; параметры остальных — в `gigacrew/tools/`.
В окружении хука — `GIGACREW_PROJECT_DIR` и `CLAUDE_PROJECT_DIR` (корень проекта; в
`cmd.exe` — `%GIGACREW_PROJECT_DIR%`).

Ответ хука — код выхода: `0` — успех, `2` — блокировка (причина — stderr; остальные хуки события после неё
не запускаются; у `PostToolUse` она уходит модели как замечание, и хуки идут все — замечания складываются;
у `Stop` — возвращает модель к работе, не больше 5 раз за ход; у `SessionStart`, `SessionEnd`, `PreCompact` и
`Notification` блокировать нечего — это предупреждение), прочие коды и таймаут — предупреждение, работа идёт
дальше. Простой текст в stdout становится контекстом у `UserPromptSubmit` и `SessionStart`. Вместо него можно
вывести JSON: `decision: "block"` и `reason`, `systemMessage` (показать пользователю),
`hookSpecificOutput.additionalContext`, а у `PreToolUse` — `hookSpecificOutput.permissionDecision`: `deny` (с
`permissionDecisionReason`), `ask` (спросить вас всегда, минуя рецензента и сохранённые разрешения) или `allow`
(без вопроса и без рецензента; опасные команды и запрет режима плана хук не снимает). JSON должен быть
единственным выводом в stdout: похожий на JSON, но не разобранный вывод — предупреждение, а у `PreToolUse` — ещё
и вопрос вам о вызове. `updatedInput` не поддерживается. Фоновые процессы хука останавливаются через секунду
после его выхода.

Хуки запускают команды без вопросов: хуки проекта приходят вместе с репозиторием, а в
`~/.gigacode/settings.json` команду может дописать и сама модель (через `run_shell`). Поэтому gigacrew
показывает команды новых и изменённых хуков и спрашивает разрешение — одним вопросом для хуков пользователя и
проекта. Ответ запоминается в `~/.gigacode/trusted_hooks.json`: для хуков пользователя — один на все
проекты, для хуков проекта — по проекту; после правки файла gigacrew спросит снова. Без терминала и в `-p`
неподтверждённые хуки пропускаются; `--trust-hooks` разрешает все хуки на один запуск (например, в CI). Настройки читаются при старте: `/hooks` показывает действующие хуки, `/hooks reload`
перечитывает файлы.

## Разработка

```sh
make dev      # пакет и dev-группа (pytest, линтеры, mypy)
make format   # автоисправления ruff и форматирование
make check    # все статические проверки и офлайн-тесты — как в CI
```

Набор проверок — по образцу [wemake-django-template](https://github.com/wemake-services/wemake-django-template):
ruff и wemake-python-styleguide (стиль и сложность), mypy `--strict`, import-linter (слои пакета —
`.importlinter`), codespell и typos, yamllint, dotenv-linter, deptry; `make audit` — известные уязвимости
зависимостей (pip-audit). Настройки — в `pyproject.toml` и `setup.cfg`.
